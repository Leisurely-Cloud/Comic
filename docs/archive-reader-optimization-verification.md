# 压缩包读取优化验收记录

实现与性能测量：2026-10-23。提交前复核：2026-10-29。

## 修改及边界

原实现每次读取图片都重新创建 `ZipArchive` 并解析全部条目，页读取分配量随归档条目数增长。现在每次明确打开归档时解析一次目录，保留会话内的条目索引，读取时临时绑定新打开的文件流，结束后释放文件句柄。缓存不存储图片内容、不解压到磁盘、不修改源文件。

同一会话的 ZIP 流定位与解压使用串行读取租约，CRC 运算在释放租约后执行，因此不同页的 CRC 可以并行。排队取消不会释放其他任务的锁；关闭后拒绝新租约，等待既有租约安全退出再释放缓存。两个独立归档互不阻塞。扫描失败或完成扫描后被取消的未注册会话也释放缓存。

文件长度与修改时间检查保留；每页复查所选中央目录记录、EOCD / ZIP64 尾部摘要，以及首次读取后缓存的本地文件头摘要。每次仍验证图片长度与 CRC32。ZIP64 条目偏移支持原长、压缩长字段的四种 sentinel 组合；大小与条目数量限制不变。

## 性能样本

使用 .NET 9 Release 独立控制台，直接编译修改前快照及当前服务，在同一进程读取相同合成归档；不包含 WinUI 布局或图片解码。归档有 4 张 stored 图片，每张 1 MiB，其余为空文本条目。先预热，再交替运行 3 轮，每轮读取 12 页，返回字节通过 SHA256 比较。下表为三轮均值的中位数，分配量由 `GC.GetTotalAllocatedBytes` 测得，包含返回图片数组和测试摘要开销。

| 条目数 | 修改前单页均值中位数 | 修改后单页均值中位数 | 修改前每页分配 | 修改后每页分配 |
| --- | ---: | ---: | ---: | ---: |
| 1000 | 4.11 ms | 2.52 ms | 约 1.53 MiB | 约 1.01 MiB |
| 20000 | 29.78 ms | 2.55 ms | 约 11.84 MiB | 约 1.01 MiB |

20000 条目样本的读取耗时约为原来的 1/11.7，每页分配量减少约 91.5%。4 页并发样本中，20000 条目归档每页均摊耗时从 13.88 ms 降至 1.25 ms；1000 条目归档从 1.73 ms 降至 1.39 ms。并发数字表示吞吐均摊，不能当作单个请求延迟。

缓存有内存成本：在两个独立进程测量 50000 张各 1 字节图片的极端条目样本，打开期间托管内存增量约从 7.1 MiB 增至 25.3 MiB，关闭并回收后两者都回落到约 23 KiB 增量。该数字是合成样本的进程内观察，不是实际漫画库的内存上限。首次打开耗时仍包含目录解析和摘要构造；本次主要优化重复页读取。

本机测量受运行时和系统负载影响，不能推断所有设备、所有压缩格式或实际界面翻页都获得同样倍数。未对真实漫画书库进行压力测试。
